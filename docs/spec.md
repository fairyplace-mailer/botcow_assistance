## 1. Общие сведения



### 1.1. Название проекта



**BotCow — автономный ассистент-разработчик на базе OpenAI, GitHub и Vercel.**



### 1.2. Цель проекта



Создать автономного бота-разработчика, который:



* имеет постоянный доступ к приватному репозиторию `fairyplace-mailer/botcow_assistance` (GitHub);

* умеет читать и изменять код, создавать ветки и Pull Request’ы;

* умеет работать с GitHub Issues/Projects (проектный менеджмент);

* интегрирован с процессом деплоя на Vercel (деплой, redeploy, статусы);

* общается с владельцем через чат (SPA + PWA) на русском языке;

* максимально берёт на себя рутинные задачи разработчика, оставляя пользователю роль постановщика задач и ревьюера.



### 1.3. Границы проекта (scope)

В рамках текущей версии:

* Один пользователь-владелец (owner).

* Набор приватных репозиториев владельца на GitHub:

  * один основной репозиторий BotCow: `fairyplace-mailer/botcow_assistance`;
  * дополнительные приватные репозитории того же владельца (рабочие проекты).

* BotCow всегда работает с одним «активным» репозиторием:

  * по умолчанию: `fairyplace-mailer/botcow_assistance`;
  * по запросу пользователя или по конфигурации backend активным может быть любой другой разрешённый репозиторий.

* Backend хранит список разрешённых репозиториев и репозиторий по умолчанию.

* Полный цикл работы для активного репозитория:
  от вопроса в чате → анализ кода → изменения в репо → PR → тесты → деплой/preview.

## 2. Термины и сокращения



* **Ассистент, бот** — OpenAI-модель(и), настроенные через Assistants API (с перспективой миграции на Responses API).

* **Сервис-прослойка (backend)** — Node.js-сервис на Vercel, через который бот ходит в GitHub, Vercel и др. API.

* **Клиент** — SPA + PWA на Next.js, чат-интерфейс пользователя.

* **Репозиторий проекта** — `fairyplace-mailer/botcow_assistance`.

* **PAT** — GitHub Personal Access Token (Classic).

* **Deployment** — деплой на Vercel (preview/prod).

* **CI/CD** — GitHub Actions для тестов и вспомогательных процессов.

* **Tools** — функции backend’a, доступные ассистенту через function calling (GitHub, Vercel, PM-операции).

## 3. Целевое окружение и стек



### 3.1. Репозиторий и структура



* Боевой репозиторий:



  * GitHub: `fairyplace-mailer/botcow_assistance` (приватный).

  * Моно-репозиторий:



    * фронтенд (Next.js SPA + PWA);

    * backend (Node.js REST API);

    * конфигурации GitHub Actions;

    * документация (`README.md`, `ARCHITECTURE.md`, `CHANGELOG.md`, `TODO.md` и др.).



* Архитектура должна позволять:



  * добавить поддержку других приватных репозиториев того же владельца (через конфигурацию).

#### 3.1.1. Рабочие репозитории и конфигурация

* Backend хранит конфигурацию рабочих репозиториев:

  * репозиторий по умолчанию: `fairyplace-mailer/botcow_assistance`;
  * список дополнительных приватных репозиториев владельца, с которыми разрешено работать BotCow.

* Все GitHub-tools на backend должны поддерживать указание репозитория (например, параметр `repository` или пара `owner` + `repo`).

* Если пользователь явно не указал репозиторий, используется репозиторий по умолчанию.

* Если пользователь указал репозиторий, который не входит в список разрешённых, BotCow обязан сообщить об этом и не выполнять операций с кодом.


### 3.2. Стек технологий



**Фронтенд:**



* Next.js 16, App Router (страница чата в режиме SPA, Client Components).

* TypeScript.

* PWA:



  * `manifest.json` (иконки, название, цвета);

  * `service worker`:



    * кеширование статики;

    * хранение последних сообщений оффлайн;

    * support install-prompt (установка на устройство).



**Бэкенд:**



* Node.js 22 (runtime Vercel).

* TypeScript.

* Лёгкий фреймворк — Express или аналог с REST-эндпоинтами.

* Деплой backend как Serverless Functions/Edge Functions на Vercel.



**Интеграции:**



* GitHub REST API (v3) + при необходимости GraphQL API.

* Vercel REST API (deployments, statuses, redeploy).

* OpenAI Assistants API (с учётом последующей миграции на Responses API).



**Хостинг:**



* Vercel Hobby (frontend + backend).



### 3.3. Хранение секретов



Секреты **только** в переменных окружения Vercel:



* `OPENAI_API_KEY`

* `GITHUB_PAT_BOTCOW` (или `GITHUB_TOKEN`, выбрать одно имя и использовать последовательно)

* `VERCEL_TOKEN`

* `BOTCOW_ACCESS_TOKEN` (токен для единственного пользователя)

* Дополнительные конфиги (при необходимости): `BOTCOW_DEFAULT_REPO`, `BOTCOW_OPENAI_ASSISTANT_ID` и т.п.



Запрещено:



* хранить секреты в коде/репозитории;

* логировать значения токенов.

## 4. Роли и модель пользователей



### 4.1. Роль: Владелец-пользователь



* Один пользователь (owner).

* Роль пользователя:



  * постановщик задач;

  * ревьюер PR;

  * при необходимости — инициатор ручных действий (мёрдж, деплой) поверх автоматизации.

* Доступ к веб-чату только по токену `BOTCOW_ACCESS_TOKEN`.

* Способы передачи токена:



  * HTTP-заголовок `X-Access-Token`;

  * возможно HTTP Basic (опционально, не обязательно в первой версии).

* Первая версия: только один токен/пользователь.

* Архитектура backend должна позволять:



  * в будущем добавить таблицу пользователей/токенов;

  * маппинг «пользователь → набор репозиториев / прав».

## 5. Общая архитектура решения



### 5.1. Компоненты



1. **Frontend (Next.js SPA + PWA)**



   * Страница чата.

   * Отправка сообщений на backend.

   * Получение и отображение ответов (включая промежуточные статусы «бот думает»).

   * Обработка ошибок (нет сети, ошибка сервера).



2. **Backend (сервис-прослойка)**



   * REST-API для фронта (chat endpoint).

   * REST-API для OpenAI tools (GitHub, Vercel, PM, вспомогательные).

   * Обёртка над OpenAI API (создание/управление ассистентом/сессиями).

   * Логирование и обработка ошибок.



3. **OpenAI Assistants**



   * Ассистент(ы) с системным промптом.

   * Набор tools (function calling) для доступа к backend-функциям.

   * Логика выбора моделей (routing).



4. **GitHub**



   * Репозиторий `fairyplace-mailer/botcow_assistance`.

   * GitHub API для чтения/записи.

   * GitHub Actions (CI):



     * тесты;

     * линтеры;

     * e2e (опционально);

     * BotCow должен уметь работать с несколькими приватными репозиториями владельца. Конкретный активный репозиторий выбирается по конфигурации backend и/или по запросу пользователя.



5. **Vercel**



   * Хостинг фронта и backend’a.

   * API для:



     * получения статусов деплоев (prod/preview);

     * запуска/повторного деплоя (redeploy).



### 5.2. Потоки данных (в общих словах)



1. Пользователь → фронт:



   * вводит сообщение в чат → запрос на backend (`POST /api/chat`).



2. Backend → OpenAI:



   * создаёт/продолжает сессию ассистента;

   * передаёт сообщение пользователя и контекст.



3. OpenAI → tools:



   * при необходимости ассистент вызывает tools:



     * GitHub (чтение/запись);

     * Vercel;

     * PM-операции;

     * служебные (логирование, системная информация).



4. Tools → внешние API:



   * backend вызывает внешние REST API;

   * возвращает результаты ассистенту;

   * ассистент формирует ответ пользователю.



5. Ответ пользователю:



   * backend возвращает текст (и, при необходимости, структурированный JSON) в фронт;

   * фронт отображает ответ в чате.

## 6. Функциональные требования



### 6.1. Общие сценарии



1. **Вопросы по проекту**



   * Примеры:



     * «Где реализована авторизация?»

     * «Опиши архитектуру проекта простыми словами».

   * Ожидаемый результат:



     * текстовый ответ;

     * ссылки на файлы/строки (формат: `path/to/file.ts:строка`);

     * по запросу — карта проекта (структура модулей, импорты).



2. **Планирование и реализация задач**



   * Пользователь формулирует задачу:



     * «Добавь страницу /pricing…»;

     * «Сделай рефакторинг этого компонента…».

   * Ассистент:



     * анализирует релевантный код;

     * описывает план работ;

     * создаёт ветку `feature/...`;

     * вносит изменения;

     * создаёт Pull Request с описанием и инструкцией по тестированию.



3. **Фикс багов по логам**



   * Пользователь прикладывает лог/ошибку (текст) + контекст (prod/preview).

   * Ассистент:



     * ищет причину в коде;

     * предлагает фикс;

     * создаёт ветку и PR.



4. **Рефакторинг и улучшение качества**



   * Примеры:



     * «Разнеси этот компонент на три части…»;

     * «Найди модули без тестов и предложи план покрытия».

   * Ассистент:



     * анализирует код;

     * предлагает план;

     * частично/полностью реализует изменения в коде через PR.



5. **Документация**



   * Обновление:



     * `README.md`

     * `ARCHITECTURE.md`

     * `CHANGELOG.md`

     * `TODO.md`/`docs/*`

   * Генерация:



     * архитектурного описания;

     * changelog’а по последним PR.



6. **Проектный менеджмент**



   * Работа с GitHub Issues/Projects:



     * создание, обновление, закрытие задач;

     * разбиение задач на подзадачи;

     * проставление приоритетов;

     * ведение roadmap (в Issues и/или отдельных файлах).



7. **Работа с деплоем (Vercel)**



   * Получение статусов деплоев (prod/preview).

   * Связка PR → preview:



     * ожидание сборки превью;

     * добавление ссылки и статуса в описание PR.

   * Redeploy:



     * инициирование redeploy по deployment ID.



### 6.2. Работа с кодом (ассистент-разработчик)



**Обязательные возможности:**



* Чтение кода:



  * получение структуры репо;

  * чтение файлов по пути;

  * поиск по содержимому (full-text search).

* Изменение кода:



  * создание ветки `feature/...` от указанной base-ветки (по умолчанию: `main`/`master`);

  * добавление/изменение/удаление файлов;

  * формирование коммитов;

  * создание Pull Request.



**Требования к PR:**



* Описание должно включать:



  * краткое summary (что сделано);

  * детали изменений (по шагам);

  * инструкции по тестированию (manual/e2e);

  * ссылку на preview (если есть);

  * при необходимости — список потенциальных рисков.



### 6.3. Тесты и качество (GitHub Actions)



**Обязательные элементы:**



* Настроить минимум один workflow:



  1. **CI-workflow для тестов и линтера**:



     * триггеры:



       * `pull_request` в основной ветке;

       * при необходимости — `push` в `feature/*` для ранней проверки.

     * действия:



       * установка зависимостей;

       * запуск линтера;

       * запуск unit-тестов (`npm test`/`pnpm test`).

     * результаты:



       * статус в GitHub Checks;

       * логи доступные через API для ассистента.



* Опционально:



  * e2e-тесты (Playwright, Cypress), запуск через отдельный workflow.



**Функции ассистента:**



* `run_tests()`:



  * триггерит соответствующий workflow (через GitHub API либо через push/dispatch).

* Анализ результатов:



  * читает статус workflow;

  * при ошибках:



    * вытаскивает логи;

    * объясняет пользователю причину;

    * предлагает фиксы.



### 6.4. Работа с Vercel и деплоем



**Возможности:**



1. **Статусы деплоев**



   * Получать список последних деплоев по окружениям (prod, preview).

   * Для каждого deployment:



     * ID;

     * статус (building, ready, error и т.п.);

     * URL (preview/prod);

     * время деплоя.



2. **Связка с PR**



   * При создании PR по ветке `feature/...`:



     * ассистент ожидает появления preview-деплоя (по событию GitHub/Vercel или через периодический опрос);

     * проверяет статус сборки (успех/ошибка);

     * добавляет в описание PR:



       * ссылку на preview URL;

       * краткий статус (OK/ошибка).



3. **Redeploy / Deploy**



   * Ассистент может:



     * инициировать redeploy по deployment ID (через Vercel API);

     * по запросу пользователя:



       * «Сделай redeploy продукта»;

       * «Откати на предыдущий успешный deployment».



### 6.5. Документация и «память» проекта



Ассистент должен использовать репозиторий как долговременную память:



* Поддерживать в актуальном состоянии:



  * `README.md` (запуск, переменные окружения, сценарии использования).

  * `ARCHITECTURE.md` (описание архитектуры и ключевых flow).

  * `CHANGELOG.md` (описания изменений по релизам/PR).

  * `TODO.md` или аналог (список задач/идей).

* По запросу пользователя:



  * генерировать/обновлять архитектурные описания;

  * формировать changelog на основе списка PR;

  * предлагать и обновлять roadmap.



### 6.6. Проектный менеджмент (PM-функции)



* Работа с GitHub Issues:



  * создание, обновление, закрытие Issues;

  * привязка PR к Issues;

  * установка лейблов и приоритетов.

* Roadmap:



  * может храниться:



    * как набор Issues c метками/Projects;

    * либо как файл `ROADMAP.md`.

* Сценарии:



  * «Создай набор задач на личный кабинет…»;

  * «Разбей фичу X на подзадачи и создай Issues».

## 7. Требования к backend / API



### 7.1. Общие требования



* Backend реализуется как REST API на Node.js/TypeScript (Express или аналог).

* Разделение:



  * публичный API для фронта;

  * внутренний API/tool-функции для ассистента (вызываются только через OpenAI function calling).

* Валидация входных данных (например, zod / class-validator).



### 7.2. Публичные эндпоинты для фронтенда (примерный контракт)



1. `POST /api/chat`



   * Вход:



     * `message: string` — текст запроса пользователя;

     * `sessionId?: string` — идентификатор сессии (для контекста чата);

   * Заголовки:



     * `X-Access-Token: BOTCOW_ACCESS_TOKEN`.

   * Выход:



     * `sessionId: string`;

     * `messages: Array<{ role: 'user' | 'assistant' | 'system', content: string }>`;

     * `status: 'in_progress' | 'done' | 'error'`;

     * `error?: string`.



2. `GET /api/health`



   * Простая проверка доступности backend.



*(При необходимости можно добавить эндпоинты для отладки, но они не обязательны в первой версии.)*



### 7.3. Backend-tools для ассистента (функции)



**Важно:** названия/сигнатуры нужно оформить в виде JSON-схем для function calling.



#### 7.3.1. GitHub-tools



Примеры функций (минимальный набор):



* `github_get_repo_structure()`



  * Выход: дерево директорий/файлов.



* `github_list_files(path?: string)`



  * Выход: список файлов/подпапок по пути.



* `github_get_file(path: string)`



  * Выход: содержимое файла (base64 или текст + метаданные).



* `github_search_in_repo(query: string)`



  * Выход: список совпадений (файл + фрагмент кода).



* `github_get_recent_commits(limit: number)`



* `github_create_branch(name: string, from_branch: string)`



* `github_update_file(path: string, content: string, branch: string, message: string)`



* `github_delete_file(path: string, branch: string, message: string)`



* `github_create_pull_request(branch: string, base: string, title: string, body: string)`



* `github_comment_on_pr(pr_number: number, body: string)`



* `github_merge_pull_request(pr_number: number, method?: 'merge' | 'squash' | 'rebase')`



* `github_run_workflow(workflow_id: string, ref: string, inputs?: object)`

  (для запуска CI, включая `run_tests()`)



* `github_get_workflow_status(run_id: string)`



* `github_create_issue(title: string, body: string, labels?: string[])`



* `github_update_issue(issue_number: number, fields: object)`



*(Имена можно упростить, главное — чёткое документирование.)*



#### 7.3.2. Vercel-tools



* `vercel_get_latest_deployments(target: 'production' | 'preview', limit?: number)`

* `vercel_get_deployment_status(deployment_id: string)`

* `vercel_trigger_deploy(project_id?: string, git_commit_sha?: string)`

* `vercel_redeploy(deployment_id: string)`



#### 7.3.3. PM-tools



* `pm_list_todos()`

* `pm_add_todo(item: { title: string; description?: string; priority?: 'low'|'medium'|'high' })`

* `pm_update_todo(id: string, fields: object)`

* (опционально) `pm_generate_roadmap(...)`



#### 7.3.4. Служебные tools



* `log_event(type: string, payload: object)` — запись важного события в Blob/логи.

* `get_config()` — ограниченный доступ к статическим настройкам (без секретов).

## 8. OpenAI-интеграция



### 8.1. Набор моделей



Используемые модели:



* `gpt-4.1` — сложные задачи анализа/архитектуры.

* `gpt-4.1-mini` — быстрые, лёгкие запросы, бытовые ответы.

* `gpt-o3-mini` — задачи, где важна точность reasoning и генерации кода.



Выбор модели — динамический на backend:



* по типу задачи (классификация запроса);

* по ожидаемому объему контекста/сложности;

* по необходимости экономии токенов.



### 8.2. Assistants / Responses API



* Первая реализация — Assistants API.

* В ТЗ заложить:



  * чёткую структуру tools/контрактов;

  * слой абстракции над OpenAI, чтобы перейти на Responses API без переписывания бизнеса.



### 8.3. Системный промпт (поведение бота)



**Требования:**



* Промпт должен быть:



  * хранится в конфигурации (файл, ENV, либо в коде в одном месте);

  * задокументирован в `ARCHITECTURE.md`;

  * доступен для обновления без переписывания всей логики.



**Общие принципы поведения:**



* Роль: старший разработчик + DevOps-бот.

* Полный цикл:



  * анализ кода;

  * подготовка плана;

  * изменения;

  * PR;

  * тесты;

  * деплой.

* Приоритеты:



  * максимальная автономность;

  * не ломать прод;

  * не удалять код без необходимости;

  * сложные/опасные изменения — согласовывать с пользователем.

* Стратегия:



  * перед изменениями:



    * читать связанные файлы;

    * формировать краткий план для пользователя (по возможности).

  * при изменениях:



    * всегда работать в новой ветке `feature/...`;

    * оформлять PR с понятным описанием и инструкцией по тестированию.

  * при ошибках:



    * анализировать логи;

    * указывать вероятную причину;

    * предлагать конкретные изменения.



**Черновик текста системного промпта (для реализации, можно уточнять):**



> «Ты — BotCow, ассистент-разработчик.

> Пользователь — не программист. Объясняй решения простым языком.

> Всегда работай через предоставленные тебе tools: не придумывай данные, а получай их из репозитория и внешних API.

> Перед изменениями:

> — находи и читай связанные файлы;

> — формируй краткий план действий;

> — создавай отдельную ветку feature/...;

> — объясняй пользователю вероятную причину;

> — предлагай конкретные изменения в коде.

Разработчик обязан оформить промпт в конфигурации Assistants/Responses и приложить его текст в документацию.

## 9. Требования к интерфейсу (Frontend)



### 9.1. Общие требования



* Один экран чат-интерфейса с элементами:



  * область истории сообщений (scrollable);

  * поле ввода текста;

  * кнопка отправки;

  * индикатор работы бота (spinner / «Ассистент думает…»);

  * (опционально) быстрые кнопки-пресеты:



    * «Сделать код-ревью»;

    * «Обновить документацию»;

    * «Собрать changelog» и т.п.



* Язык интерфейса: **русский**.



* Поддержка:



  * десктоп браузеры (Chrome, Firefox, Safari, Edge);

  * мобильные браузеры (Safari iOS, Chrome Android).



### 9.2. PWA



* `manifest.json`:



  * name, short_name;

  * иконки (минимум 192x192, 512x512);

  * theme_color, background_color;

  * display: `standalone`.

* `service worker`:



  * кеширование статики;

  * оффлайн-режим для последних N сообщений (например 20);

  * обработка install-prompt (для установки на домашний экран).



### 9.3. Дизайн



* Стиль: «минимально аккуратно».



  * светлая тема по умолчанию;

  * спокойная палитра (синий/фиолетовый + серый фон);

  * округлые карточки сообщений;

  * ограниченная ширина контейнера (например, 800–1000px) с адаптивом под мобильные экраны.

* Логотип/брендинг:



  * можно использовать временные placeholder’ы;

  * архитектура верстки должна позволять легко заменить их на реальные.

## 10. Безопасность



### 10.1. Секреты и токены



* Все токены и ключи только в ENV Vercel.

* Запрещено:



  * выводить PAT, OpenAI API key, Vercel Token в логи;

  * отдавать их на фронт.



### 10.2. Авторизация



* Каждый запрос к `/api/chat` должен проверять:



  * наличие и корректность `X-Access-Token`.

* При ошибке:



  * возвращать 401/403 с безопасным сообщением (без утечки технических деталей).



### 10.3. Доступ к репозиториям



* PAT должен иметь минимально достаточные права:



  * `repo`, `workflow`, `issues`, `project` (по необходимости).

* Возможность ограничить список репозиториев, с которыми работает ассистент (конфигурация).



---



## 11. Нефункциональные требования



### 11.1. Производительность



* Средний ответ на «типичный» запрос (чтение нескольких файлов, простой анализ/план):



  * до **10–15 секунд**.

* Тяжёлые операции (скан репо, генерация тестов и т.д.):



  * могут занимать дольше;

  * фронт должен корректно отображать «бот думает»;

  * желательно информировать пользователя, что задача тяжёлая.



### 11.2. Надёжность и обработка ошибок



* При rate limit GitHub/OpenAI:



  * ассистент сообщает пользователю о временном лимите;

  * предлагает повторить позже или автоматически попробовать ещё раз (конфигурируемо).

* При ошибках Vercel:



  * отображать текстовые сообщения, доступные в API;

  * при необходимости — предлагать шаги по исправлению.

* При падении отдельного tool:



  * ассистент не должен «ломаться»;

  * возвращает пользователю понятное сообщение.
